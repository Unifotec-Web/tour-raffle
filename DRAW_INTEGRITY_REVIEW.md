# Internal draw-integrity engineering review

Scope: local/test draw processing on branch `codex/draw-integrity-review`, starting from `9f784e0`. This is an engineering review, **not** independent audit certification. Production draw mutations remain disabled by `APP_ENV` and the opt-in `ENABLE_LOCAL_DRAW` gate.

## Findings and changes

1. **Preapproval outcome preview.** At `9f784e0`, preparation committed a 256-bit seed. The API did not return it, but a database reader could calculate winners before an admin approved the snapshot. Migration `0005_draw_seed_approval` makes the seed and seed hash nullable during preparation. Approval now verifies the frozen snapshot and commits `secrets.token_bytes(32)`, its SHA-256 hash, the approver, timestamp, state change, and audit event together. New prepared runs have no seed, so their outcomes cannot be calculated from stored draw data before approval. PostgreSQL triggers reject setting a seed on a prepared row without the `prepared → approved` transition and reject changing it afterward. Already prepared rows created under `0004` retain their original seed; approval now fails closed with a manual-review response rather than silently replacing that seed. There is no in-app reset or rerun path.
2. **Algorithm drift on retry.** The run recorded an algorithm version, but selection previously used the code's current constant. A future algorithm update could have changed an approved run's winners after an interrupted attempt. Execution now passes the recorded version to selection and rejects an unsupported version or a mismatch with the snapshot. Future versions need an explicit versioned implementation that preserves `hmac-sha256-entry-weighted-v1`; unknown versions fail without writing winners.
3. **Misleading failure audit after commit.** An exception while building the HTTP response after a successful commit previously wrote `draw.failure`. The failure handler now re-reads durable state and logs a processing failure only when the run remains `approved`. A lost response after commit is recovered by retrying the endpoint, which returns the persisted winners without another execution or failure event.

## Seed custody and preview boundary

The seed is generated by Python's `secrets.token_bytes(32)` during the admin approval transaction. It is stored as 32 raw bytes in `draw_runs.seed`; `seed_hash` is SHA-256 of those bytes. It is never returned by the API, including admin and public responses. The hash is null before approval and is available as a commitment afterward. A PostgreSQL trigger validates seed length and hash at first assignment, rejects later seed/hash changes, and protects the recorded approver and timestamps. The application checks seed length and hash again before execution.

The seed is **plaintext in the database**. A database reader can preview outcomes after approval and before execution. A database owner or superuser can bypass triggers; the snapshot hash and seed hash are stored in the same database, so they are not an independent tamper-evidence anchor. Database encryption/key custody, separation of duties, external timestamping, and independent verification are future production design decisions. A hash commitment alone does not prove that an approver did not choose or inspect a favorable outcome; the application generates one seed per approved run and provides no API reroll.

## Snapshot, selection, and reproducibility

Preparation locks the campaign row, requires a closed campaign, reconciles all entries with `current_entries`, checks confirmed entries and redeemed owned coupons for active participants, and requires at least `winner_count` distinct participants. It stores a single snapshot per campaign. Entries are queried in ascending PostgreSQL UUID order of `Entry.id`. Each entry contains string `entry_id`, `user_id`, and `coupon_id`; the snapshot also contains campaign ID, `updated_at`, critical capacity/prize/date/price rules, eligibility text, winner policy, and algorithm version. `json.dumps(sort_keys=True, separators=(',', ':'), ensure_ascii=True)` produces canonical ASCII JSON; SHA-256 covers its UTF-8 bytes. Approval and execution recompute the hash from the stored bytes. Normal updates/deletes of snapshot rows are rejected by PostgreSQL; privileged tampering of content alone is caught by the hash check. A privileged actor able to rewrite both content and hash can evade this check.

For each rank, `hmac-sha256-entry-weighted-v1` computes HMAC-SHA-256 with the frozen seed as key and ASCII message `hmac-sha256-entry-weighted-v1:<counter>`, starting counter at zero and incrementing for every block, including rejected blocks. It interprets the 32-byte digest as a big-endian integer. For a pool of size `n`, values at or above `2^256 - (2^256 mod n)` are rejected; the accepted value modulo `n` selects one entry uniformly without modulo bias. The selected entry is recorded with its rank, then every remaining entry for that participant is removed while preserving the order of others. Thus a participant holding `m_i` of `N` entries has first-pick probability `m_i/N`. At each later pick, a still-eligible participant's probability is their remaining entry count divided by the remaining pool size. These are sequential weighted picks without replacement **by participant**: multiple entries improve selection chance, but one participant receives at most one win. PostgreSQL also enforces unique `(run_id, user_id)`, `(run_id, entry_id)`, and `(run_id, rank)`.

The unique `draw_runs.campaign_id` constraint prevents another run for the same campaign. Prepare retries return the same snapshot; approve retries return the same approved seed commitment; execute retries use the same stored snapshot, seed, and version. The application never reconstructs the snapshot from live entry rows during recovery. A future algorithm deployment must retain the old versioned implementation to resume old approved runs; the current code instead fails closed if it encounters a version it cannot execute.

## Transactions and publication

Preparation locks the campaign row. Approval, execution, and publication lock the run row with `SELECT … FOR UPDATE`, so concurrent requests serialize. Execution inserts all winners, moves the run to `completed`, and writes its success audit event in one transaction. A failure before commit rolls back every winner row and leaves the approved seed/snapshot for deterministic retry; a separate `draw.failure` event is attempted when the database remains available. A process crash may leave no failure event, but the durable `approved` state is explicit. A lost response after commit leaves `completed` plus the winners; retry returns them. Concurrent executions produce one result set and one success event. Publication is a separate idempotent transaction; concurrent publication creates one event. If publication races execution, it either waits and publishes the completed result or returns 409 while execution finishes. It cannot expose partial winners.

Admin draw details can show selected entry and participant IDs after execution, before publication; admin authorization is required. Public `/api/v1/draws/published` returns only published campaign metadata, counts, hashes, version, and timestamps. It does not return seeds, entry IDs/codes, coupon IDs/codes, participant IDs, or winner records. `/api/v1/draws/mine` requires a valid session and returns only that user's published winning entry codes. Public winner profiles and consent-driven publication remain unimplemented.

## Verification and remaining limits

A disposable PostgreSQL 16 instance was migrated from empty through `0005_draw_seed_approval`. Targeted tests cover no seed before approval, immutable postapproval seed, seed/snapshot tamper rejection, unique run creation, concurrent prepare/approve/execute/publish, execute/publication race, lost responses after commit, rollback before commit, deterministic retries, version mismatch fail-closed behavior, entry weighting, participant uniqueness, legacy prepared runs, permissions, production guard, and public/private response boundaries. The full backend suite passed **26 tests**; the unchanged frontend build passed with lint and TypeScript checks. Existing Pydantic, passlib, SQLAlchemy, and httpx deprecation warnings remain. Commands:

```bash
docker compose -f backend/compose.verify.yml up -d
cd backend
DATABASE_URL=postgresql://tour_raffle_verify:local-verify-only@127.0.0.1:55432/tour_raffle_verify .venv/bin/alembic upgrade head
PYTHONPATH=. TEST_DATABASE_URL=postgresql://tour_raffle_verify:local-verify-only@127.0.0.1:55432/tour_raffle_verify .venv/bin/pytest -q
cd ..
npm run build
```

The design still relies on a single admin approval, keeps the seed in plaintext in the database after approval, and has no external randomness or audit anchor. Official rules approval, payment/order reconciliation, eligibility screening beyond stored flags, production scale testing, and a publication/privacy review gate are unresolved. No payment, public coupon issuance, prize claim, notification, or draw production enablement was added.
